# Revised Project Description — Agentic Metamorphic Testing Framework for Computer Vision Models

## 1. Project Overview

Our FYP proposes a **general-purpose, domain-adaptive Agentic Metamorphic Testing (MT) Framework for Computer Vision (CV) models**.

The framework is designed to test different types of CV models, including:

* **Classification**
* **Object Detection**
* **Image Segmentation**
* **Object Tracking**

The user provides four primary inputs:

1. **Trained CV model**
2. **Model/task type**
3. **Dataset**
4. **Domain description**

The addition of the **domain description** is important because the framework is not restricted to a fixed set of metamorphic relations. Instead, it combines a predefined library of general-purpose MRs with **LLM-generated generative, environmental, semantic, and domain-specific MRs** that are appropriate for the particular application.

The overall system operates as an **adaptive closed-loop testing framework**: testing results are stored in memory, the accumulated evidence is analyzed, and an agent dynamically determines what should be tested next.

# 3. User Input

The framework accepts four major inputs.

## 3.1 CV Model

The user provides a trained computer vision model.

The framework should use a **model adapter interface** so different model frameworks can be supported.

For example:

```text
PyTorch
TensorFlow
ONNX
Ultralytics
Hugging Face
```

The POC can initially support a limited number of model formats.

---

## 3.2 Model Type

The user specifies the task:

```text
Classification
Detection
Segmentation
Tracking
```

This information is essential because the expected output relation and MR oracle are different for each task.

For example, a rotation may mean:

**Classification**

```text
cat → cat
```

**Detection**

```text
bounding boxes must rotate consistently
```

**Segmentation**

```text
segmentation mask must rotate consistently
```

**Tracking**

```text
object identity and trajectory must remain consistent
```

# 5. Domain Description

The user also provides a **natural-language domain description**.

For example:

> "This is an autonomous driving object detection model that detects pedestrians, cars, cyclists, and traffic signs in urban road scenes. The model should remain robust under changes in weather, lighting, camera conditions, object appearance, and partial occlusion."

The domain description is used by the MR Discovery Agent to understand:

* what objects exist;
* what environmental conditions matter;
* which changes should preserve semantics;
* which changes should alter the expected output;
* what transformations are meaningful;
* what transformations could be unsafe or invalid.

This makes the framework **domain-adaptive rather than tied to one specific domain**.

# 8. MR Discovery Agent

This is a major part of the revised architecture.

The framework does **not** assume that only the original 21 MRs can be tested.

The 21 MRs form the **initial/general-purpose MR library**.

The MR Discovery Agent receives:

```text
Domain Description
+
Task Type
+
Model characteristics
+
Base MR Library
```

and generates an expanded MR candidate pool.

The candidate pool consists of:

```text
1. Existing/general MRs
2. Generative/environmental MRs
3. Domain-specific MRs
```

# 12. MR Types

The framework should support multiple types of metamorphic relations.

## Type 1 — Invariant

The transformation should not substantially change the prediction.

$$
O' \approx O
$$

Example:

```text
brightness change
```

---

## Type 2 — Predictable Transformation

The output changes according to a known transformation.

$$
O'=T(O)
$$

Example:

```text
image rotation
```

where detection bounding boxes or segmentation masks must rotate accordingly.

---

## Type 3 — Addition

An object is inserted.

$$
O'=O+\Delta
$$

Example:

```text
insert pedestrian
```

---

## Type 4 — Removal

An object is removed.

$$
O'=O-\Delta
$$

---

## Type 5 — Relational

The relationship between original and transformed outputs must satisfy a defined condition.

$$
R(O,O')=True
$$

This is particularly useful for tracking and complex scene transformations.

---

# 13. MR Validation

An important component is the **MR Validator**.

An LLM-generated MR should not automatically become a valid test.

The validator checks:

```text
MR schema
       ↓
Task compatibility
       ↓
Domain consistency
       ↓
Transformation feasibility
       ↓
Expected output relation
       ↓
Semantic preservation requirements
```

Invalid or ambiguous MRs are rejected or sent back for refinement.

# 15. Initial Testing

The framework initially selects a small number of source images.

For example:

```text
10 representative images
```

The initial testing phase explores a subset of the available MR candidates.

This establishes an initial metamorphic testing profile.

The goal is not necessarily to exhaustively test every combination.

---

# 16. Adaptive Test Selection Agent

Once initial tests have been performed, the system enters its main agentic loop.

The Adaptive Test Selection Agent receives:

```text
Failure Profile
+
Testing Memory
+
MR Candidate Pool
+
MR Failure Rates
+
MR Coverage
+
Previous Test Results
+
Affected Classes
+
Transformation Parameters
+
Remaining Test Budget
```

It then selects:

```text
Source image
+
MR
+
Transformation parameters
```

Example:

```json
{
  "source_image": "image_743",
  "mr": "GMR-02",
  "parameters": {
    "fog_density": 0.7
  },
  "reason": "Fog has not been sufficiently explored and previous low-visibility tests caused pedestrian detection failures."
}
```

This creates the **closed-loop agentic behaviour**.

---

# 17. Transformation Engine

The selected MR is executed by deterministic transformation services.

The LLM does **not** directly manipulate the image.

For example:

```text
Agent:
MR = Blur
sigma = 3

        ↓

Transformation Engine:
apply_blur(image, sigma=3)

        ↓

Transformed image
```

This makes the framework reproducible.

---

# 18. Generative Transformation

For generative MRs:

```text
Source image
     ↓
Generative transformation
     ↓
Generated image
```

For example:

```text
Daytime scene
       ↓
Day → Night
       ↓
Generated nighttime scene
```

or:

```text
Clear road
       ↓
Clear → Fog
       ↓
Generated foggy road
```

The generative transformation service can be implemented through a pluggable image-generation/editing model.

---

# 19. Semantic Validation

Generative transformations can unintentionally change objects or scene semantics.

Therefore the transformed image is validated before model testing.

The system can use:

* CLIP;
* image-text similarity;
* object preservation checks;
* spatial consistency;
* task-specific constraints.

For example:

```text
Original:
1 car + 2 pedestrians

Generated:
1 car + 2 pedestrians

Semantic validation:
PASS
```

But:

```text
Original:
1 car + 2 pedestrians

Generated:
1 car + 1 pedestrian

Semantic validation:
FAIL
```

The generated image can then be rejected or regenerated.

# 20. CV Model Execution

Once the transformed image passes validation:

```text
Original image
       ↓
CV Model
       ↓
Original output

Transformed image
       ↓
CV Model
       ↓
Transformed output
```

Both outputs are passed to the task-specific MR oracle.

# 21. Task-Specific MR Oracle

The oracle determines whether the metamorphic relation was satisfied.

## Classification

Example:

```text
Original → Dog
Transformed → Dog
```

PASS.

---

## Detection

Transform the expected bounding boxes and compare against predicted boxes.

$$
IoU(B_{expected},B_{predicted})
$$

---

## Segmentation

Transform the expected mask and compare against the predicted mask.

$$
IoU(M_{expected},M_{predicted})
$$

or Dice.

---

## Tracking

Compare:

```text
object identity
trajectory
position
association consistency
```

between the original and transformed sequences.

---

# 22. Failure Analyzer

When a violation occurs, the system records detailed information.

Example:

```json
{
  "image": "image_743",
  "mr": "fog",
  "parameter": 0.7,
  "status": "FAIL",
  "affected_class": "pedestrian",
  "original_confidence": 0.91,
  "transformed_confidence": 0.43,
  "semantic_validation": 0.94
}
```

The analyzer can categorize the failure as:

```text
confidence degradation
class confusion
object disappearance
false positive
false negative
localization degradation
segmentation degradation
identity switch
```

depending on the task.

# 24. Closed-Loop Learning

The most important part of the architecture is the feedback loop:

```text
             TEST
              ↓
           RESULT
              ↓
        PASS / FAILURE
              ↓
        FAILURE ANALYSIS
              ↓
           MEMORY
              ↓
       UPDATED PROFILE
              ↓
        AGENT REASONING
              ↓
          NEXT TEST
              ↓
             TEST
```

Therefore, the testing process becomes progressively **evidence-guided**.

For example:

```text
Initial tests
      ↓
Agent discovers:
blur causes pedestrian failures
      ↓
Memory updated
      ↓
Agent selects:
different blur strengths
+
images containing pedestrians
      ↓
More evidence
      ↓
Agent may discover:
failure occurs only at high blur
```

This is much more informative than simply applying every transformation uniformly.

$$

# 29. Separation of Responsibilities

A very important architectural principle is:

| Component                    | Responsibility                                   |
| ---------------------------- | ------------------------------------------------ |
| **LLM / MR Discovery Agent** | Generate and reason about candidate MRs          |
| **MR Validator**             | Check whether generated MRs are valid/applicable |
| **Adaptive Agent**           | Select next image + MR + parameters              |
| **Transformation Engine**    | Actually transform images                        |
| **Generative Model**         | Generate/edit images                             |
| **CLIP**                     | Semantic validation                              |
| **CV Model**                 | Produce predictions                              |
| **MR Oracle**                | Objectively determine MR satisfaction            |
| **Failure Analyzer**         | Categorize failures                              |
| **Memory**                   | Store historical evidence                        |
| **Profiler**                 | Build/update robustness profile                  |
| **Orchestrator**             | Coordinate the complete process                  |

The LLM therefore **does not become the source of truth** for whether a test passed.

The objective oracle determines that.

The conceptual contribution of the framework is not simply:

> "Apply image transformations to a CV model."

Instead, the proposed system combines:

$$
\boxed{

+
\text{LLM-generated MRs}
+
\text{Domain descriptions}
+
\text{Generative transformations}
+
\text{Task-aware oracles}
+
\text{Semantic validation}

The 21 existing MRs act as the **initial knowledge base**, while the LLM can extend the testing space through **generative/environmental and domain-specific MR discovery**.

before it becomes an executable test.

# 32. Final One-Paragraph Description

> **We propose a general-purpose, domain-adaptive Agentic Metamorphic Testing Framework for Computer Vision models. The framework accepts a trained CV model, its task type, a dataset, and a natural-language domain description. It first evaluates the model on the original dataset to construct an initial failure profile. An MR Discovery Agent then combines a predefined library of 21 general-purpose metamorphic relations with generative/environmental transformations and new domain-specific MRs inferred from the supplied domain description. These candidate MRs are validated for task compatibility, semantic preservation, and executability before entering the MR candidate pool. The framework then performs an initial set of tests and stores all testing evidence in persistent memory. An Adaptive Test Selection Agent uses the failure profile, previous test outcomes, MR coverage, failure statistics, and domain information to dynamically select the next source image, MR, and transformation parameters. The selected transformation is executed by deterministic transformation or generative services, and generated images are validated using CLIP and task-specific semantic constraints. The original and transformed inputs are then evaluated by the CV model, and a task-specific metamorphic oracle objectively determines whether the expected relation is satisfied. Failures are analyzed and stored back into memory, creating a closed feedback loop in which each testing cycle informs the selection of subsequent tests. At the end, the framework produces an evidence-based robustness and failure profile identifying vulnerable classes, transformations, environmental conditions, and failure patterns, together with recommendations for further model improvement and testing.**
